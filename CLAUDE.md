# Hub World Game

A game where the player walks around a room and interacts with objects that open
mini-games (chess, hangman, tic-tac-toe, more later).

## Tech stack
- Python (Flask) backend, HTML/CSS frontend.
- Game rules and state live in Python. JavaScript is fine wherever it makes the
  game work or feel better (movement, input, sending moves without reloading,
  sounds). Everything working well matters more than keeping JavaScript minimal.
- python-chess for chess rules.
- All styling lives in CSS files. Colors and fonts are CSS variables in one
  theme file so the whole look can be changed in one place.

## Aesthetic
Cozy, cute, cottagecore top-down pixel art. Reference images (for mood only):
`docs/aesthetic/cozy-room.jpg` (the main reference for the room),
`docs/aesthetic/cherry-garden.jpg`, `docs/aesthetic/pink-farm.jpg`.

- **Perspective:** top-down with a slight 3/4 view. The room is seen from above,
  with the back wall visible along the top and a thick pastel-pink frame around it.
- **Palette:**
  - Pastel pink and rose: walls, frame, bedding, cushions, tablecloths, bows
  - Mint and sage green: rugs, poufs, plants, hedges, grass
  - Cream and ivory: furniture, benches, tables, fences, panels
  - Warm medium browns: herringbone wood floor, bookshelves, plant stands
  - Small accents: cherry red, warm fireplace orange/yellow, white and lavender flowers
- **Style:** chunky, crisp pixels with soft outlines in dark brown or plum (never
  pure black). Shade with a few flat color steps, not smooth gradients.
  Shapes are soft and rounded.
- **Room contents:** pink back wall with curtained windows, a wreath and plant
  shelves; herringbone wooden floor; a bed with a pink quilt; bookshelves; a
  fireplace; a tea table with benches; rugs and lace doilies; poufs; lots of
  potted plants and flowers. Interactable objects for the mini-games should fit
  in (for example, chess on the tea table).
- **Mini-games:** use the same palette. UI panels are cream cards with a pink
  border, buttons are pink or mint, and boards use pink/cream (chess) or a
  wooden look.
- **Fonts:** a pixel font (for example "Pixelify Sans" or "Press Start 2P"),
  saved in `static/fonts/`.
- **Implementation:** use `image-rendering: pixelated`, draw sprites small and
  scale them up by whole numbers. All colors are variables in `theme.css`.
- **Originality:** all art is our own. The references set the mood. Never copy
  their sprites, characters or layouts.
- **Mood:** warm, wholesome and calm, like a sunny afternoon in a cute cottage.

## Architecture
- Scene system: the room is one scene, each mini-game is its own scene.
- Every mini-game follows the same interface. Adding a game = one new folder in
  games/ + one object in the room.
- Controls: arrow keys/WASD to move, E to interact, Esc to return to the room.
- Rooms: every `room/rooms/<name>.py` that defines `room = Room(...)` is a
  room (found automatically, shown at `/rooms/<id>`). `room/objects.py` holds
  what all rooms share. The current room is kept in the Flask session, so `/`
  (where Esc and "Back to the room" go) returns to the room the player was in.
  Rooms are joined by `Exit`s (doors); walking into one fades to the
  matching door in the other room.
- `app.py` finds games automatically: every `games/<name>/routes.py` that
  defines `game = SomeMiniGame()` is registered. Never edit `app.py` to add a game.
- Game state lives in the Flask session. Games are plain HTML forms that POST
  to the game's routes; `static/js/scenes.js` sends them in the background and
  swaps in the new `<main>`, so there is no page reload.
- Pixel art is grids of letters (`room/sprites.py`). Each letter is a color
  variable in `theme.css`. Games add their own grids to `sprites.SPRITES` and
  draw them with `sprites.render(name)`.
- Sounds are generated by `tools/make_sounds.py` into `static/sounds/`. A page
  plays one by putting `data-sound="<name>"` on an element
  (open, back, select, move, win, lose, draw, door). `crackle` is a loop for
  the fireplace scene; pages can check `scenes.isMuted()` and listen for
  `sound:toggle` to start or stop a looping sound.

### Adding a new mini-game
1. Create a label `<name>` and a branch `game/<name>` from the latest `main`.
2. Make `games/<name>/` with `__init__.py`, `routes.py` (a `MiniGame` subclass
   with `slug`, `title` and `register_routes`, and `game = ...` at the bottom),
   `logic.py` (pure Python rules), `templates/<name>.html` (extends
   `base.html`, uses `.panel` and `.button`) and `static/<name>.css`.
3. Add `tests/test_<name>.py` for the rules and the routes.
4. Add a piece of furniture for it in a room file in `room/rooms/` with
   `game="<slug>"` and `prompt="play ..."`. Until the game exists, the object
   opens the "coming soon" placeholder. The room tests check that every game
   object can be reached on foot. If a placeholder object for the game is
   already in a room (the kitchen's sink, fridge, pantry and table, or the living room's piano and card table), just
   give the game the same slug and it connects by itself.
5. Play a sound on moves and at the end of a game with `data-sound`.

## Running and testing
- Setup and run steps are in SETUP.md. The server runs on port 5050
  (http://127.0.0.1:5050) because macOS uses port 5000.
- Run `python -m pytest` before every PR, and try the change in the browser.

## Git and GitHub workflow
- Code is hosted on GitHub. Use the GitHub CLI (`gh`) for issues and pull requests.
- Never commit directly to `main`.

### Branch structure
- `main`: the stable game. Only finished, tested games get merged here.
- `room`: the hub world (player, movement, collisions, interactable objects).
- One long-lived branch per game, created from `main`:
  `game/tictactoe`, `game/hangman`, `game/chess`, and so on for new games.
- Issue branches are created FROM the branch they affect and merged BACK INTO it:
  - Issue about chess → branch from `game/chess`, PR back into `game/chess`.
  - Issue about the room → branch from `room`, PR back into `room`.
  - Issue name format: `<issue-number>-short-description` (e.g. `12-chess-ai`).

Example:
    main
     ├── room
     │    └── 1-player-movement → PR into room
     ├── game/chess
     │    ├── 10-chess-board     → PR into game/chess
     │    └── 12-chess-ai        → PR into game/chess
     └── game/hangman
          └── 7-word-list        → PR into game/hangman

### Keeping branches up to date
- Whenever something new reaches `main`, bring `main` into `room` and every
  `game/*` branch before starting new work there. Do it with an issue branch
  (`<number>-sync-main-into-<branch>`) that merges `main` and opens a PR into
  that branch. Always merge, never copy files across, so all branches share
  history and later merges into `main` stay clean.
- If an issue builds on a PR that isn't merged yet, branch from that PR's
  branch instead and start the PR description with "Depends on #<PR>".
  Tell me the order to merge them in.
- If a merge conflicts, resolve it on a branch and explain what you kept.
  Never ask me to resolve conflicts on GitHub.

### Issues
- Every piece of work starts as a GitHub issue with a description and
  acceptance criteria.
- Label each issue with the game it belongs to (e.g. `chess`, `hangman`, `room`)
  so it's clear which branch it goes into.
- Before starting an issue, pull the latest version of its parent branch.
- GitHub only closes an issue automatically ("Closes #N") when the PR is
  merged into `main`. After I merge PRs into `room` or a `game/*` branch,
  close their issues with a comment saying which PR did the work.

### Commits and pull requests
- Small commits with clear present-tense messages ("Add castling to chess").
- Do NOT add "Co-Authored-By" lines or any AI attribution to commits or PRs.
- Issue PRs target the parent branch (NOT main) and include "Closes #<number>".
- When a game is fully done, open a PR from `game/<name>` into `main`.
- Never merge anything yourself. Wait for me to test and merge.

## Working style
- I'm [a beginner / somewhat experienced], so explain what each new file does.
- Stop after each issue so I can test it before moving on, unless I say to
  keep going (for example while I'm away). Then keep working through the
  issues, stacking branches as described above, and give me the merge order
  at the end.
- Always tell me exactly how to run the project after changes.
